## 二、本机比小鱼方案更靠前的入口（重要）

4.1.10.27 里有一条**完整的、自带请求构造的发送函数**，不需要我们自己拼任务对象：

```
0x4EB0B90   发朋友圈（mmsnspost / cmdId 209）
```

证据链：

1. `0x4EB1065`：`mov dword ptr [rbp+0x3A0], 0xd1` —— 0xD1 = 209，写进 CGI 上下文；
2. `0x4EB0CDC` / `0x4EB0CE3`：`lea` 到 `"kernel::foundation::CoCgiSendRequest"` 与 `"mm_cgi.h"`（日志标签）；
3. `0x4EB0D1C`：`call 0x4DB9D20` = **`SnsPostRequest` 构造函数**（首条指令 `mov [rcx], vtable`，随后初始化 `+0x48/+0x58/+0x70/+0x80/+0x98`）；
4. 函数体里调用 `0x680D0FC`（分配）、`0x4EB1AE0`、`0x4EB2450`、`0x4EB1C00`、`0x4DBB010` 等；
5. **唯一直接调用者 `0x4EAE7F0`**，而 `0x4EAE7F0` 出现在这次发布的首触调用栈里（见下）。

## 三、发布链（动态实测，协程线程）

用守卫页 + 单步重布，对 `0x4D90000–0x4DC0000`（48 页，空闲时 0 执行）做覆盖，
抓到 2419 个唯一执行地址、27 个函数，并按首触栈还原出完整链路：

```
0x3CDC50   协程调度        （字符串：zlog / co_main / co_core.cpp / coroutine start）
 → 0x3CEE10   (0x2A)       间接调用 [rax+0x350]，协程 resume
   → 0xCC2080   (0x13B)     任务状态机（flag [rcx+0x188] / [rcx+0x17B] / [rcx+0x179]）
     → 0x29E32A0  (0x97)      shared_ptr 释放 + 虚调用 [rax+0x50]
       → 0x4EAB7D0  (0x1818)   含 "publish_" / "publish_data" / "true" / "false"
         → 0x4EAE7F0  (0x16F3)   protobuf 组装
           → 0x4EB0B90  (0xB30)    ← 命令号 209，真正发出 mmsnspost
```

**这解释了此前所有失败**：发布不在 UI 线程上跑，而是在协程池线程里（实测 tid `0x2754`）。
所以字符串守卫、UI 线程栈采样、`thread` 级断点全都看不到发送动作。

## 四、实测手段清单（都在 `data/workspace/components/wechat-moments/`）

| 文件 | 用途 |
| --- | --- |
| `hwbreak.c` → `build/moments-hb*.dll` | 守卫页 + 单步重布：入口布防（`HbArm`）、区域覆盖（`HbCoverSpan`）、参数内存两级快照（`HbArgsDump`） |
| `sampler.c` | 线程栈采样（10ms 周期 `RtlVirtualUnwind` 展开，按栈签名去重） |
| `inject.py` | 注入 + 调用无参/单参导出 |
| `tools/hb-run.mjs` | `arm / cover / dump / profile / clear` 编排 |
| `tools/sample-run.mjs` | 采样编排 |

几条踩过的硬约束（已写进代码注释，别再试）：

- 硬件断点 DR0 在 VEH 里改 CONTEXT **不能可靠生效**，会原地死循环；
- 守卫页必须靠**单步重布**，否则同页其它代码会把守卫用掉；
- **不能布防自己模块所在页**，异常处理器在里面会无限递归到栈溢出；
- 栈展开必须用 CONTEXT **副本**，否则 Rip/Rsp 被改坏，返回后执行流跑飞；
- 这版核心 `.rdata` 里 endpoint 字符串**零引用**，静态定位不可行，只能动态。

## 五、还缺什么

1. `0x4EB0B90` 的**参数签名**：入口时 `rcx` 是返回值缓冲（`mov [r15+0x30]` 这类写入），
   栈上 `[rbp+0x490]` 指向一个含两个 int 的结构。需要一次真实发布时的参数快照来确定。
2. 若走“自己构造任务”的老路，还需要：CGI 模板、任务构造函数、`ParseFromArray`、
   proto 偏移、root 全局与 vtable[5] dispatch —— 这 5 个在 4.1.10.27 尚未定位。
3. 更现实的路线：**录制-回放**。抓到一次发布的参数结构后，把正文替换成我们的内容再调用
   `0x4EB0B90`，避免重建整个任务对象。

## 六、实测补充：三层入口的真实参数（2026-11-10）

用标记 `WBTEST-20261110-1130` 发一条，同时布防三层，命中数据（原始快照见
`build/hwargs-3layer.txt`、`build/needle-hits.txt`）：

```
tid=0x2754  rip=0x4EAB7D0  args=(0x17D9812EFC0, 0x2, 0x20, 0x40)
tid=0x2754  rip=0x4EAB7D0  args=(0x17D9812EFC0, 0x3, 0x607A184DC438, 0xC5A9FF180)
tid=0x2754  rip=0x4EAE7F0  args=(0x17D9812EFC0, 0xC5A9FEED0, 0x607A184DC438, 0x1)
tid=0x2754  rip=0x4EB0B90  args=(0xC5A9FEBD0, 0x17D849C13C0, 0xC5A9FE920, 0xC5A9FEB50)
```

结论：

- `0x4EAB7D0` 是**同一个对象的方法**，第二个参数是 2/3 这类**步骤号**——它是一个按步推进的发布状态机；
  对象 `0x17D9812EFC0` 的布局：`+0x00` vtable `0x7FF8C7CFD308`、`+0x08` 自身、`+0x10` 子对象 `0x17D9812EFB0`、
  `+0x18` `0x7FF8C7903DF8`、`+0x20` `0x17D92AA5940`、`+0x28` `0x2`。
- `0x4EAE7F0` 收同一个 `this`，第四个参数是 `1`。
- `0x4EB0B90` 的 `rcx/r8/r9` 都是**协程线程栈地址**（`0xC5A9F…`），发布结束即失效；
  `rdx` 指向的堆结构走进去是 mars/MMKV 网络配置（`mmkv_key_head_img_url`、`default-longlink`），
  说明它是 CGI 发送器的网络上下文，**不是发布参数**。
- 标记在进程里有 24 份副本，其中 `0x17D9245B2C8`、`0x17D9245D870`、`0x17D9245DB18` 等同处一段堆，
  疑似请求 proto 的序列化缓冲；另有栈副本 `0xC5A9FBB62`。
- 发布状态机对象在发布完成后即被释放（事后读回已是残留），因此**必须命中时抓取**，不能事后补读。

## 七、这意味着什么

“原样回放捕获到的参数”**不可行**（栈地址已失效）。要在 4.1.10.27 上真发，只剩两条：

**A. 自建任务对象（小鱼原法）** — 还缺 4 个常量：
CGI 16 字节模板、CGI 任务构造函数、`ParseFromArray`、任务里 proto 的偏移、
以及网络管理器的 root 全局与 vtable[5] dispatch。
已有：`operator new` = `0x680D0FC`、`SnsPostRequest` 构造 = `0x4DB9D20`、发送器 = `0x4EB0B90`。

**B. 驱动发布状态机** — 需要拿到 `0x17D9812EFC0` 这类对象的**构造函数**与它的入参结构，
然后在微信进程里“自己起一次发布”。难点同样是对象构造。

两条路的共同瓶颈都是“把参数对象造出来”，差别在于 A 造的是 CGI 任务、B 造的是发布状态机。
A 更接近小鱼已验证过的路径，B 更省事但对象关系更复杂。

## 八、发布对象族（静态反推，2026-11-10）

从 `0x7FF8C7CFD308` 反算 vtable RVA（模块基址 `0x7FF8BF1A0000`）得到 `0x8B5D308`，
再全库搜“谁引用它”，一次把整族对象挖出来了：

| 函数 | 大小 | 作用 |
| --- | --- | --- |
| `0x29E2B30` | 0xAF | **上下文对象**构造：vtable `0x8763DF8`；子对象在 `+0x18/+0x28/+0x98/+0xA8`；`+0x118=0x64(100)`、`+0x128=0` |
| `0x2D42A00` | 0x104 | **工厂**：`ecx=0x278` 调 `0x680D0FC`（operator new）→ **sizeof(发布对象)=0x278**；写 refcount `0x100000001`、vtable `0x87C0AC8`；再调 `0x4EAB1D0` 构造；返回 shared_ptr |
| `0x4EAB1D0` | 0x159 | **发布对象构造**：写 vtable `0x8B5D308`；初始化 `+0x140/+0x160/+0x180/+0x1D8/+0x1F8/+0x218`；**`+0x1A8` 是 std::string（容量字段 `+0x1C0` 初值 0xF，即 SSO）**；把入参 shared_ptr 存到 `+0x258/+0x260` |
| `0x4EAB7D0` | 0x1818 | **状态机步骤**：`(this, step, arg3, arg4)`，实测 step=2、3 |
| `0x4EAE7F0` | 0x16F3 | 组包步骤：`(this, …, …, 1)`，内部调 `0x4EB0B90` |
| `0x4EB0B90` | 0xB30 | **发送器**：建 `SnsPostRequest`(0x4DB9D20)、写 cmdId 209、`CoCgiSendRequest` |
| `0x4EAB480` | 0x125 | 发布对象析构（还原 vtable，释放 `+0x250/+0x260` 的 shared_ptr，析构 `+0x1A8` 的 string） |

调用关系：

```
0x29E2B30  造上下文
   ↓ shared_ptr
0x2D42A00  造发布对象（0x278 字节，内部 0x4EAB1D0）
   ↓
0x4EAB7D0  step=2 → step=3 → …（按步推进）
   ↓
0x4EAE7F0  → 0x4EB0B90  发 mmsnspost(209)
```

## 九、离“能发”还差什么（精确版）

已具备：sizeof(发布对象)=0x278、分配器、上下文构造、发布对象构造、步骤函数、发送器。

还缺 **两点语义**（不是地址）：

1. **步骤号与参数的含义**：实测只见到 step=2（arg3=0x20, arg4=0x40）与 step=3（arg3=堆指针, arg4=栈指针）；
   step=1/4/5… 是否存在、各自要什么，需要把 `0x4EAB7D0` 里的 switch 反出来。
2. **正文写入点**：`+0x1A8` 的 std::string 是候选，但需要确认是哪个 setter 写它、以及写入的是正文还是别的字段。

这两点都可以用现成工具在**不崩微信**的前提下拿到：布防 `0x4EAB7D0` 抓所有步骤（含 step=1 与后续），
同时布防 `0x4EAB1D0` 后的 setter 候选，看 `+0x1A8` 何时被写。
